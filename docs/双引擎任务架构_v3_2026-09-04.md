## 1. 结论

Vibe Research 有三条执行路径，不是两个完整研究引擎二选一：

| 路径 | 责任 | 模型 | 典型任务 |
|---|---|---|---|
| Browse / Deterministic | 浏览、登记数据源刷新、确定性计算 | 不调用 | 看页面、刷新数据、计算指标 |
| Quick | 在已备齐的文本材料中定位相关段落 | 直连 API | 按目标筛选已有材料段落（v1） |
| Deep | 开放取证、跨来源验证、多步长任务 | Codex Harness、Claude Code 或 WorkBuddy 本机 Agent | 从零调研、补证据、处理冲突、六阶段研究 |

当前 `DirectStageAgent` 能用直连 API 执行六阶段，它属于 **Direct Deep 实验适配器**，
不是 Quick。这批代码保留，但不再用它定义 Quick 的验收标准。

## 2. 四个维度必须分开

| 维度 | 当前取值 |
|---|---|
| 用户入口 | UI / CLI / API / MCP |
| 系统内部路由提示（兼容旧请求） | auto / quick / deep |
| 执行路径 | deterministic / quick / deep |
| 模型与付费 | ChatGPT 订阅 / API key / 兼容网关 / 本地模型 |

`provider` / `model` / `apiKey` / 底层 `engine` 不进 `ResearchTask`。任务先按语义路由，
然后才由目标适配器选取可用的运行时配置。

## 3. 两层契约，不再混用一个 Engine 概念

### 产品层：ResearchTask / Task Router / ExecutionEngine

- `ResearchTask`：描述目标、任务类型、取证范围、流程形状、安全材料引用和期望输出；
  Browse / Refresh / Calc 还必须携带类型化 `operation`，不能靠自然语言猜要调用哪个程序。
  它不携带原始正文、文件路径或调用方自报的 `materialState`。
- `TaskMaterialResolver`：在服务端逐条核对材料存在性、类型与授权，返回绑定版本的解析结果；
  `ready / partial / missing` 只从这份结果派生；`ready` 还必须绑定材料版本和文本 / 非文本模式。
- `QuickMaterialLoader`：只在路由进入 Quick 后读取已授权版本，并交付由可信服务端解析器预切的
  净化文本段落。Quick 执行器不接收磁盘路径，也不从整篇正文猜段落边界。
- `TaskOperationRegistry`：用真实查询 / 端点 / 计算注册表校验确定性操作是否存在、参数是否可执行。
- `TaskRouter`：只在服务端启动时注入上述两个可信依赖。每次 HTTP 请求只能提交任务，
  不能提交 resolver、operation registry 或 `ready` 结果；材料解析后的判定部分保持纯函数。
- `ExecutionEngine`：消费已路由任务，产出统一事件流；恢复运行必须同时核对不可变运行 ID 与
  绑定任务、材料版本的路由指纹。Quick 和 Deep 各有一个适配器。

### 六阶段内部：EngineLifecycle / AgentRunner

现有 `engine.ts` 和 `runner.ts` 只负责「已经决定跑六阶段研究以后，
怎么准备引擎环境并执行单个 stage turn」。它们是 Deep 的内部实现，不是产品层路由器。

## 4. 内部自动路由规则

1. `browse_data` / `refresh_registered_data` / `calculate` 直接走确定性程序。
2. 只有 `locate_passages` 满足以下全部条件时走 Quick：服务端确认材料全部 `ready` 且为文本、
   最多 16 份、只用现有证据、单步工作流、输出格式为文本。
3. 材料缺失或部分缺失、需要开放式找新证据、或需要多步调查时走 Deep。
4. 兼容 API 显式要求 Quick 而任务不符合时，当场拒绝并说明原因，**不静默改用 Deep**。
5. 兼容 API 显式要求 Deep 可以将有界分析升级为深度执行。
6. 确定性任务不因全局 Agent 开关而浪费模型额度。

路由只用结构化任务元数据，第一版不让 LLM 判断该走哪条路，避免账单、速度和执行保障在用户不知情时改变。

## 5. 统一格式不等于统一份量

三条路径共用 `TaskEvent` 与后续 `TaskResult` 信封，但产物按任务类型可选：

- Browse 可以只返回页面数据或确定性计算。
- Quick v1 返回模型筛选的完整材料段落与绑定版本的引用；产物明确标成
  `model_selected_passages / non_exhaustive`，并在正文提示“不是摘要，也不代表材料全貌”。
- Deep 返回报告、证据、计算、冲突、manifest 和完整运行记录。

「共用 schema」不得被解读成「Quick 也必须跑六阶段并写完整报告」。

## 6. 借鉴结论

实时查看了三个成熟开源实现：

- [Vercel AI SDK Provider Registry](https://github.com/vercel/ai/blob/main/packages/ai/src/registry/provider-registry.ts)：
  借鉴「上层通过注册表获取能力，不把 provider 写进业务任务」。
- [OpenAI Agents JS Runner](https://github.com/openai/openai-agents-js/blob/main/packages/agents-core/src/run.ts)：
  借鉴「Runner 与 ModelProvider 分开，每次运行单独传 maxTurns / signal / session」。
- [LangGraph JS](https://github.com/langchain-ai/langgraphjs)：它解决更重的持久化图执行与恢复。
  本仓库已有六阶段状态机、事件账本和 validator，引入它会形成第二套状态真理源。

决策：**不增加新运行时依赖**；只借鉴边界形状，在现有 Core 上建最小契约。

## 7. 与行业 Plugin 的关系

`ResearchTaskKind` 只表达跨行业通用动作（浏览、定位段落、摘要、比较、抽取、深研）。
行业 Plugin 后续以可选契约声明：

- 这个行业允许哪些 Quick 任务；
- 每种任务可以看哪些资料和工具；
- 输出 schema 与 validator；
- 页面入口与 eval 用例。

不恢复一套独立旧项目，也不把 Plugin 改回无类型 YAML 配置。
