## 1. 执行失败收尾

新增引擎无关的 `research_failure.ts`，只识别执行器错误通道，不扫描模型正常回答或来源正文。

| 错误 | 行为 | 用户下一步 |
| --- | --- | --- |
| 明确使用限额 / 额度耗尽 | 当前阶段立即停止，不再执行后续阶段和 gate 重写 | 等待恢复，或自己在设置换模型后新开研究 |
| 登录 / API 凭据失效 | 立即停止 | 重新登录或检查密钥，测试连接后新开研究 |
| 明确限流 / 响应超时 | 在既有尝试上限内重试；达到上限则停止后续阶段 | 检查连接、稍后再试或自己换模型 |
| 模型错误同时伴随不可修复的取数契约错误 | 上游不可修复性优先，停止本次运行，不把失败带到后续阶段 | 保留两类错误供诊断 |
| 未识别错误 / 正常资料缺口 | 不猜成额度、登录或超时，保留既有校验流程 | 按原始诊断处理 |

普通阶段沿用 `maxRetries + 1` 次尝试，合规重写沿用独立的 `gateRetries` 上限；本批没有改变客户默认超时配置。
本批真实验证参数是每轮 5 分钟、每阶段最多一次重试、最多一次 gate 重写，不代表所有用户都采用此时限。
旧订阅 CLI 的 `agent_quota` 已把额度与频率限制合并，无法反推出精确原因时保持原有立即停止行为。
不会暗换模型、供应商或登录态。超时后重新发起是**新运行，不是断点续跑**；已落盘资料不删除。

同时修复：

- Codex 已收到明确错误时，后续 worker 退出不再覆盖真正原因；用户取消仍优先。
- `manifest.failure_code` 使用固定枚举，HTTP 状态接口只按枚举提供固定中文恢复提示，不转发自由错误正文。
- 订阅执行器抛出的类型化异常也保留失败码；取数异常里出现“429 / timeout”不会被误认为模型错误。
- 成稿 turn 失败但遗留正文校验通过时，不能被最终状态重算改回成功。
- gate 重写已修好正文但随后执行失败时，仍保留失败状态及原因，不能进入成功知识归档。

验证覆盖：额度/登录首次停止、超时与限流上限停止、超时恢复后继续、上游与执行混合失败、流错误保留、
成稿假成功阻断、gate 中的未知/超时/额度失败、API 固定提示与未知码不透传。
